## 1 · The defect — an over-long `q` answered 502 (`036ca48`)

**Found by probing, not by reading.** A 6000-character `q` came back `502 Bad Gateway`. Bisecting the input
located the boundary and confirmed it was deterministic, not a transient:

| `GET /search?q=<n chars>` | 200 | 800 | 1024 | 2000 | 3000 | 4000 | 5000 | 6000 | 6000 ×3 |
|---|---|---|---|---|---|---|---|---|---|
| Status | 200 | 200 | 200 | 200 | **502** | **502** | **502** | **502** | **502 / 502 / 502** |

Scoping it further showed the trigger was fuzziness, not request size: at 6000 characters `/autocomplete`
(prefix matching), `/suggest` (suggesters), and the `category` / `location` term filters all answered **200**,
and so did 6000 characters of *short words* on `/search`. Only a single long token failed.

**Cause.** No DTO in the project declared a maximum length — `grep` for `MaxLength` across
`src/presentation/*/dto/` returned nothing, only numeric bounds. So the term reached the `multi_match` with
`fuzziness: AUTO` (design D3), Lucene refused to build the fuzzy automaton for it, Elasticsearch answered 400,
and `AllExceptionsFilter` mapped **every** `ResponseError` to 502 regardless of the status the engine reported.

**Why it mattered beyond the status line.** The response was a 5xx, so it logged at `error` level with a stack
(design D10 behaviour, correct in itself) — any client could fill the error log and point monitoring at a
cluster that was healthy the whole time, all within its 60 req/min budget. Neither scanner could have caught
it: ZAP tests injection payloads, not lengths, and CodeQL sees no vulnerability here.

**Fix, in two independent layers.**

1. Length caps declared once in `presentation/common/input-limits.ts` and applied by the query DTOs — 256 for
   free text, 128 for filter terms, 20 subcategories. The oversized term never leaves the edge.
2. A 400 *from* Elasticsearch maps to 400 instead of 502. A rejected query is the caller's doing; a 404
   (missing index), a 401/403 (our credentials) and any 5xx are not, and those keep their 502.

**Pinned at two levels:** a table-driven DTO spec (9 cases, including the exact 3000-character input) and an
e2e case for the wiring.

**Confirmed in production after the deploy:**

```json
{"statusCode":400,"error":"Bad Request","message":"Validation failed",
 "details":["q must be shorter than or equal to 256 characters"]}
```

## 2 · The one boundary violation — `infrastructure` imported `presentation` (`d8a6e44`)

Every layer README states the dependency rule, and a grep sweep found the codebase honours it everywhere but
one line: `infrastructure/rate-limit/rate-limit-store.module.ts` imported
`@presentation/rate-limit/throttler-store.adapter`.

The adapter was simply in the wrong place. It implements `@nestjs/throttler`'s storage contract over an
application port and holds no HTTP concern, which makes it a driven adapter like the Redis cache or the ES
search adapter. Moving it to `infrastructure/rate-limit/` closes the hexagon; the guard, which *is* an HTTP
concern, stays in `presentation/`. Pure move plus two import updates — no behaviour change.

Sweep after the fix: zero `@presentation` imports under `infrastructure/`, zero `@infrastructure` imports under
`application/`, `domain/` or `presentation/`.

## 3 · The contract gap — OpenAPI published no response schema (`21a637f`)

The spec at `/docs-json` documented its query parameters properly but described **every** response as
`{"type": "object"}`, carried **zero** entries under `components.schemas`, and documented **no error status at
all** — 2388 bytes that told a client nothing about what it would receive.

The cause was structural: the response DTOs were `interface`s, and the `@nestjs/swagger` CLI plugin can only
introspect classes. They are classes now with explicit `@ApiProperty`, which also removed a quieter problem —
the envelopes embedded application models (`ProductSummary`, `Facets`) directly, so the layer that must not
leak inward models was publishing them.

Every endpoint now declares its statuses: `@ApiOkResponse` for the body and `ApiErrorResponses(...)` for the
failures, rendering the one `ErrorResponseDto` the exception filter actually produces. `/health` is the
deliberate exception — its 503 carries the health body, not the error envelope, and says so.

| | Before | After (live) |
|---|---|---|
| Spec size | 2388 bytes | **11546 bytes** |
| `components.schemas` | 0 | **14** |
| Tags | 0 | 5 |
| `/search` responses | `200: object` | `200: SearchResponseDto` · `400/422/429/503: ErrorResponseDto` |
| `info.version` | `1.0.0` (mismatched) | `0.1.0` (matches `package.json` and `GET /`) |

The DAST job feeds ZAP this same spec, so the scan gained the error contracts too — and stayed green.

zero `any`, zero `eslint-disable`, zero `TODO`/`FIXME` in production code. Type-aware lint exits 0.

**Contract behaviour**, probed live — every one of these was the documented behaviour:

| Request | Status |
|---|---|
| `?foo=bar` (unknown param) | 400 with `property foo should not exist` |

**Security headers**, verified on a live response: HSTS `max-age=31536000; includeSubDomains`, `nosniff`,
`X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: no-referrer`, COOP + CORP `same-origin`,
`X-XSS-Protection: 0` (correct modern practice), plus `RateLimit-Limit/Remaining/Reset` on every response.
CORS is closed in production: `Origin: https://evil.example` receives no `Access-Control-Allow-Origin`.

**Dependencies.** `npm audit`: **0 total** across dev and prod. Only two majors sit behind, both pinned on
purpose and justified (`@elastic/elasticsearch` to match the 8.x server, TypeScript until 7.1 restores the
programmatic compiler API).

**Resilience design.** The fail-open cache, the fail-**over** rate limiter, the critical/non-critical split in
`/health`, the process safety net and the explicit ES timeout/retries are each documented with the reasoning
for the choice *and* for the alternative rejected. That is rarer than the code itself.

## Honest limits of this review

- **Load was not re-measured.** The p95 figures cited come from the 2026-07-23 k6 run against a local stack;
  the fixes here add a length check at the edge, which cannot make it slower in any measurable way, but that is
  reasoning, not a measurement.
- **e2e and integration were not run locally** (no Docker on the machine that day). CI ran both on every commit.
- **Rate-limit enforcement was not re-flooded in production** — deliberately, to avoid spending real budget.
  It is covered by `test/rate-limit.e2e-spec.ts` (7 cases) in CI and by `loadtest/rate-limit.js`; the live check
  was limited to confirming the `RateLimit-*` headers count down.
- **The review is black-box plus source reading.** No profiler, no mutation testing, no chaos testing of the
  managed Elasticsearch or Redis.
