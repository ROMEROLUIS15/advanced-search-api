## B. Code

### B1 — Metrics do not count 401, 429 or 404 · *highest value of the five* · **CLOSED 2026-07-28**

**Done in `e464ca6`, exactly as the approach below describes**: recording moved to an Express middleware in
`app.setup.ts`, ahead of the router and therefore of every guard; the interceptor (and its false docstring)
retired in the same commit, so nothing double-counts. Bonus the approach did not promise: traffic to the
Express-mounted `/docs` now lands in the `unmatched` bucket, shrinking B2's observability blind spot. An e2e
case asserts a guard-rejected 401 lands in the registry under its matched route. The original finding is kept
below for the record.

`MetricsInterceptor` is a Nest interceptor, so it runs **after** the guards. A request rejected by the API-key
guard or the rate limiter never reaches it, and neither does an unmatched route. The abuse signals are exactly
the ones not measured.

Confirmed on 2026-07-28: four `GET /search` requests without a key returned 401, and **none** of them appear
in `http_requests_total` in Grafana Cloud.

The interceptor's own docstring claims it "records the RED metrics for every request", which is wrong and
should be corrected with the fix.

**Approach**: measure in an Express middleware registered in `app.setup.ts`, ahead of the guards, hanging off
the response's `finish` event as the interceptor already does. Keep the route label as the *matched pattern*
(`request.route?.path`), falling back to a single `unmatched` bucket — labelling by raw URL would create one
series per distinct query. Retire the interceptor or reduce it to the part the middleware cannot see.

Watch out: the middleware must not double-count with the interceptor during the transition, and `/metrics`
itself is inside the rate limiter, so its own requests get counted.

### B2 — Swagger is outside the pipeline

`swagger.setup.ts:32` mounts `/docs` and `/docs-json` with `app.use`, so no Nest guard, interceptor or
filter runs for them. Consequences: unlimited API-key attempts against the docs, and no metrics or logs for
that traffic. The key check itself is sound (SHA-256 + `timingSafeEqual`), so brute force is not a realistic
vector; the operational blind spot is the real cost.

**Approach**: either a small rate-limiting middleware sharing `RateLimitStorePort`, or serve the document
from a guarded controller instead of `SwaggerModule.setup`.

### B3 — Index migration is not really versioned

`PHYSICAL_INDEX_SUFFIX` is hard-coded to `_v1`. There is no creation of `_v2`, no validation, no atomic alias
flip, and the seed never removes retired products. The alias *repair* landed (`84e20f5`), which is a
different thing.

**This is the only item on the list that deserves a design pass before code.** Consider `/opsx:propose`.

### B4 — `/health` is unauthenticated and unthrottled · **substance closed 2026-07-28**

Closed by `split-health-liveness-and-readiness`, though **not the way this entry proposed**. The sketch below
says to keep only `/live` fully open; that is not achievable, because Render's check is the deploy gate and
it sends no credential — polling a dependency-free `/live` would let an unseeded deployment go live and serve
503s instead of failing the deploy. So all three health endpoints stay open, and the fan-out concern is
answered instead by making the continuously polled path touch **one** dependency rather than two. The
original text is kept below for the record.

Exempt from both the API-key guard and the rate limiter, and every call fans out to a parallel Elasticsearch
and Redis probe. Severity is **low**, and deliberately so: measured on the Upstash console on 2026-07-28, the
whole database served **3,100 commands for the month** against a 500,000 free-tier allowance, so nothing is
being consumed at a rate worth defending against. An earlier estimate of ~518,000 was wrong by 170× and has
been withdrawn — see the correction in `docs/OBSERVABILITY-2026-07-27.md`.

**Approach when it comes up**: split `/live` (no dependencies) from `/ready` (dependencies), and keep only
`/live` fully open.

**Revised 2026-07-28 by H2**: the "3,100 commands for the month" figure — and the low severity resting on
it — silently assumed the instance slept most of the day (H1). Awake 24/7, Render's own ~4.3 s health
polling spends ~605k Upstash commands/month on its own. See H2 for the measured numbers and options.

### B5 — Log shipping is implemented but not switched on · **CLOSED 2026-07-28**

**Switched on and verified** — but not by just setting the variables: the first activation silenced stdout
*and* Loki at once, because the logger's readable `level` and `time` formats each break a different half of
the worker-transport pipeline, invisibly. Fixed in `7ee3757` (numeric wire format across the worker), lines
verified in Loki by `correlationId`, and the Tempo pivot executed against production. The measured numbers
and the full mechanism are in `docs/OBSERVABILITY-2026-07-27.md`. The variable block below stays valid.

The code is deployed and inert. Set on Render to activate:

```
LOKI_URL=https://logs-prod-<region>.grafana.net
LOKI_USERNAME=<numeric Grafana Cloud user id>
LOKI_PASSWORD=<Grafana Cloud token>
```

`LOKI_USERNAME` and `LOKI_PASSWORD` must be set together or not at all; the schema rejects half a credential
because Loki would answer 401 to every batch and shipping is best-effort, so the failure would be invisible.

## G. Traps found the hard way

Three measurement mistakes were made during this session. All three had the same shape — trusting a query
without checking that it measured what it appeared to — and they are recorded so the next session does not
repeat them.

1. **`span.db.system="redis"` can never match.** `@opentelemetry/instrumentation-ioredis` emits
   `db.system.name` (current semantic conventions) while `@elastic/transport` emits `db.system` (the older
   one). A query for the wrong attribute returns empty, which is indistinguishable from "no spans".
2. **TraceQL needs dotted attribute names quoted.** `span.db.system.name="redis"` returns nothing;
   `span."db.system.name"="redis"` works. The unquoted form parses as something else and fails silently.
3. **Probe traffic clusters around deploys.** Log lines and traces showing `/health` every 5 seconds were a
   deploy window, not steady state. Extrapolating that spacing across 24 hours produced a figure 170× too
   large and a finding that had to be withdrawn. Render does not poll `/health` continuously; the keep-alive
   cron does, six times an hour.

The general rule: an empty result is evidence about the query first and about the system second.

Two more from the 2026-07-28 activation session, same shape:

4. **Loki ingestion lags ~60–90 s behind the request.** The success lines "missing" from Loki minutes after
   the traffic were simply not ingested yet — the 4xx lines of the *same burst* had already appeared, which
   made the gap look selective. Re-querying two minutes later closed it. Re-measure before theorising about a
   partial drop.
5. **A silent transport must be proven, not configured.** Setting the Loki variables produced a healthy
   service whose stdout and Loki were both empty, with no error anywhere — `silenceErrors` doing its job on a
   batch that was never valid. The diagnosis that worked: reproduce with the real transport and real
   credentials, then bisect the config one knob at a time. The spec-level stubs could never have seen it.
6. **A verification window contaminated by your own traffic proves nothing.** The keep-alive fix looked
   verified 18 minutes after the deploy — until the instance napped at exactly 15 minutes past the last
   *manual* request, which is what had been holding it up. Any "it stayed alive" check must start *after*
   your own last request, not after the change. Same shape as the three above: the observation was real, the
   thing it measured was not the thing under test.

## H. New on 2026-07-28 — the keep-alive cron is throttled

- [x] **H1** · **CLOSED 2026-07-28** — GitHub runs the
      `*/10 * * * *` keep-alive roughly once an hour at best. The full run history sharpened the morning's
      estimate: gaps of 1–3.5 h routinely and up to **8h48**, with `createdAt == startedAt` and zero
      cancelled runs on every one — the ticks are never *created*, so no workflow setting can fix it, and it
      had been this way **since the cron shipped**. The "ticks land ~5 min late" belief came from watching
      two ticks on day one. That diagnosis is solid and is what the rewritten `keep-alive.yml` comments,
      CLAUDE.md and the README deploy notes now record.
      **Fix applied**: an external **UptimeRobot** monitor on `/health` every 5 minutes (3× inside Render's
      15-minute spin-down window), which also takes over the uptime-alarm role — the workflow's runs stayed
      green through every nap because its curl rides out the cold start it was meant to prevent.
      `keep-alive.yml` stays only as an hourly-ish backstop probe.
      **Verified 2026-07-28**, and the verification is worth reading because the first attempt at it was
      wrong. At **14:04:57 UTC the instance booted again** — new instance id, `/health` counter reset from
      251 to 14 — with no deploy and no cron run behind it: a spin-down, ~15 minutes after the last manual
      traffic at 13:49. Had the check been run a few minutes earlier, over a window that still contained
      that manual traffic, this would have been recorded as "fix verified". The nap was the monitor's own
      start-up gap: its **first check ever was at 14:04:22**, seconds before the instance went to sleep. From
      that point the boot lines stop: **18+ minutes of continuous uptime past the 14:19 spin-down point**,
      with the `/health` counter climbing monotonically — the monitor is holding the instance awake.
      **The trap, worth more than the fix**: UptimeRobot was first pointed at the service **root**, not
      `/health`. The root requires `X-API-Key` (the API has been private since 2026-07-27), so every check
      answered **401**, the monitor declared the service down and started emailing. Keeping the instance
      awake still worked — a 401 is inbound traffic and resets Render's idle timer just as a 200 does — so
      the *keep-alive* half was quietly fine while the *alarm* half was inverted: it now cries wolf forever,
      which is worse than the silent-green cron it replaced. It also spent rate-limit budget (`/` is not
      exempt; only `/health` is) and logged 401s under `route="/"`. Corrected to `/health` the same day.
      **When re-pointing this monitor, or adding another, the target must be `/health`** — the one endpoint
      the API-key guard and the rate limiter both skip, which is exactly why it exists.

- [ ] **H2** · **Found by fixing H1.** **Measured fact**: while an instance is running, Render's own health
      check polls `/health` every **~4.3 s** — `increase(http_requests_total{route="/health"}[5m])` = 70.0 in
      steady state, well clear of any deploy window. **Projection, conditional on H1 actually landing**: an
      instance awake 24/7 takes that to ~20,160 requests/day, and every `/health` costs one Upstash `PING`,
      so it would spend **~605,000 Redis commands/month against the 500,000 free-tier allowance** — breach in
      ~25 days, before counting real cache traffic. While the naps continue the bill stays small, which is
      the only reason this is not already burning. **Fixing H1 is what makes H2 urgent**, so land them
      together rather than celebrating one and discovering the other.
      This *revises the G3 correction*: the withdrawn "~518k/month" estimate had the poll rate right and the
      duty cycle wrong — Render does poll continuously, but only while an instance is running, and the
      instance rarely ran. It also reopens **B4's** severity call, which silently assumed the naps.
      **Options when picked up** (do not improvise a fourth):
      **(a) Memoize the health report in-process.** The TTL sets the probe rate outright, so pick it with the
      arithmetic in hand — at a 4.3 s poll, probes/month ≈ `30 × 86400 / TTL`: a **5 s** TTL only skips every
      other poll (~302k/month — under the cap with no margin, so *not* enough on its own), **30 s** gives
      ~86k, **60 s** gives ~43k. The 30–60 s band is the useful one: 7–14× cheaper, and readiness stale by at
      most a minute against deploy decisions that take minutes anyway.
      **(b) Keep Redis out of the polled path.** Point Render's `healthCheckPath` at a variant that runs the
      ES/index probe only. Redis is non-critical by design — its `PING` never changes the status code Render
      acts on — so this takes the health-driven Redis cost to **zero** while preserving the index readiness
      that gates deploys (E7). Strictly the bigger lever; (a) still helps every other caller.
      **(c)** B4's full `/live` vs `/ready` split, the most invasive. (a) and (b) compose.
      **Also measure while there**: the same ~4.3 s cadence drives an `indices.exists` call against Elastic
      Cloud (~20k/day). Nobody has checked that against its quota — do not assume it is free, and do not
      assume it is a problem either.
      This is a behavior change against the synced `service-health` spec, so it gets a small OpenSpec change,
      not a quiet commit.

      **Taken 2026-07-28: option (c)**, as `split-health-liveness-and-readiness`. `/health/ready` runs the
      critical probes only and is what `render.yaml` polls, so health-driven Redis traffic goes to **zero**
      rather than being amortised; `/health` is untouched for humans and the monitor; `/health/live` calls
      nothing. Option (a) was rejected with a reason worth keeping: the 4.3 s `PING` is an accidental
      keepalive, so removing or thinning it lets the Upstash connection idle out and a status-based probe
      would flap through every reconnect. **Still open inside this**: the ES side is unchanged at ~20k
      `indices.exists`/day and remains unmeasured — task 6.5 of the change measures it before archiving.
